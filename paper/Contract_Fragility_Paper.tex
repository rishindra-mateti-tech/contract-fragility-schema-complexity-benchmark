\begin{abstract}
Tool-augmented Large Language Models (LLMs) and autonomous agent architectures depend fundamentally on structured JSON Schema contracts to interface with external execution environments. While recent research has extensively addressed context-window exhaustion through tool retrieval and schema compression, the causal influence of tool contract design---specifically object nesting depth, optionality density, enum constraint specificity, and identifier ambiguity---remains an unstandardized empirical question. In current software engineering practice, developers author schemas through heuristic intuition, frequently introducing structural friction that induces parameter omission or schema validation rejection. This paper establishes a formal empirical benchmark protocol to evaluate contract fragility across 20 synthetic API-inspired tool specifications modeled after production REST and Model Context Protocol (MCP) standards. We propose a decoupled three-task evaluation architecture: (1) Argument Construction under isolated parameter complexity without distractors, (2) Tool Selection under domain-matched competing distractor suites with randomized presentation order, and (3) Execution Semantics evaluating recursive field-level grounding. We outline concrete structural failure hypotheses, formalize statistical evaluation metrics based on Wilson score confidence intervals and McNemar paired exact tests, and introduce an open-source static schema linter (\texttt{SchemaFragilityLinter}) to audit tool contracts prior to agentic deployment.
\end{abstract}

\section{Introduction}
\IEEEPARstart{F}{unction} calling and autonomous agent architectures have transitioned into foundational building blocks of modern software engineering. Frameworks such as Anthropic's Model Context Protocol (MCP)~\cite{anthropic2024mcp}, Google Agent Development Kit, and OpenAI Function Calling enable Large Language Models (LLMs) to query databases, invoke APIs, and trigger mutations across enterprise environments. 

Central to every function-calling interface is the \textit{tool contract}: a structured specification encoded in JSON Schema (Draft-07), defining the function identifier, semantic descriptions, parameter types, enums, and required properties. When presented with a task, the model must map natural language intent into valid, strictly conforming JSON arguments matching the target schema.

Despite the critical role of schemas in agent reliability, tool-contract authoring in industry remains largely unguided by empirical standards. Developers routinely transplant raw backend object models directly into tool definitions. While recent literature has tackled context-window bloat through tool retrieval~\cite{patil2025bfcl, sakizli2026rag, babu2026toolchoice}, the software engineering community lacks a systematic measurement of how \textit{internal contract structure} causally impacts model execution.

Benchmarks such as the Berkeley Function Calling Leaderboard (BFCL)~\cite{patil2025bfcl} evaluate model performance across static, heterogeneous schemas to rank models. However, they do not causally perturb schema properties to isolate which specific contract design choices cause failure. While recent empirical findings demonstrate that wording changes in tool docstrings can alter model selection probabilities by over an order of magnitude~\cite{toolpreferences2025emnlp}, the causal effects of object nesting, enum constraints, and optional field density remain unquantified.

\subsection{Contributions}
This paper establishes a controlled empirical evaluation protocol for contract fragility:
\begin{enumerate}
    \item \textbf{A Three-Task Decoupled Benchmark Architecture:} We decouple function-calling evaluation into three distinct, orthogonal tasks: (Task 1) Argument Construction with isolated parameter complexity, (Task 2) Tool Selection with randomized domain-matched distractor suites, and (Task 3) Execution Semantics measuring recursive field-level value grounding.
    \item \textbf{A Controlled Structural Mutation Taxonomy:} We formulate 80 controlled schema conditions derived from 20 synthetic API-inspired specifications spanning four core structural mutations: canonical flat baseline, nested hierarchy, optionality bloat, and ambiguous identifiers.
    \item \textbf{Transparent Dataset Provenance:} We provide a fully documented manifest of synthetic schemas modeled after enterprise API patterns (Stripe, GitHub, Slack, Kubernetes, AWS S3, etc.) ensuring reproducibility without operational security risks.
    \item \textbf{Static Contract Linter:} We introduce \texttt{SchemaFragilityLinter}, an open-source static analyzer that audits JSON Schema definitions for structural fragility anti-patterns prior to deployment.
\end{enumerate}

\section{Related Work}

\subsection{Function Calling Benchmarks and Model Capabilities}
The evaluation of LLMs as tool users has evolved from simple single-turn API matching to complex agent environments. The Berkeley Function Calling Leaderboard (BFCL)~\cite{patil2025bfcl} represents the standard comprehensive benchmark for model comparison across Python, REST, and SQL interfaces. ToolBench~\cite{qin2023toolbench} introduced 16,000 real-world APIs to benchmark tool retrieval and multi-step execution. These benchmarks treat schemas as fixed artifacts to evaluate models, whereas our study holds models fixed to evaluate \textit{schema design properties}.

\subsection{Tool Retrieval and Context Compression}
As tool catalogs expand, context-window overflow has become a primary bottleneck. Recent systems propose diverse retrieval mechanisms: AnyTool~\cite{du2024anytool} introduced a hierarchical API retriever, while ToolkenGPT~\cite{hao2023toolkengpt} modeled tools as specialized embedding tokens. Sakizli~\cite{sakizli2026tscg, sakizli2026rag} demonstrated that standard JSON Schema definitions overflow small context budgets, proposing deterministic token compilation (TSCG) to compress schemas by 44--57\%. In parallel, Babu and Iyer~\cite{babu2026toolchoice} introduced Causal Minimal Tool Filtering (CMTF) to expose minimal next-step tools. Our work investigates the complementary question: \textit{for the tools present in the context, how does structural contract design govern reliability?}

\subsection{Prompt Sensitivity and Wording Biases}
Recent natural language processing research highlights the sensitivity of LLMs to minor prompt phrasing. Zhang et al.~\cite{toolpreferences2025emnlp} demonstrated that small wording modifications to tool docstrings drastically alter selection behavior. This protocol extends that inquiry from natural language descriptions to formal structural schema properties.

\section{The Three-Task Evaluation Taxonomy}

\begin{figure*}[t]
\centering
\fbox{\parbox{0.96\textwidth}{
\textbf{Task 1: Argument Construction (Zero Distractors)} \\
Input: User Query + Exactly One Target Schema (Canonical, Nested, Bloated, or Ambiguous). \\
Evaluation: Strict JSON Schema Draft-07 validation via \texttt{Draft7Validator}. Metric: Syntactic Validation Pass Rate ($\text{SIR} = 1 - \text{Pass Rate}$). \\[4pt]
\textbf{Task 2: Tool Selection (Competing Distractor Suites)} \\
Input: User Query + Target Schema + Domain-Matched Distractor Tools (Randomized Menu Order). \\
Evaluation: Top-1 Tool Selection Accuracy ($\%$) comparing Canonical vs. Ambiguous names, controlling for positional bias. \\[4pt]
\textbf{Task 3: Execution Semantics (Recursive Field-Level Value Grounding)} \\
Input: Syntactically Valid Outputs from Task 1. \\
Evaluation: Recursive field-by-field Exact Match ($\text{EM}$), Precision, and Recall against ground-truth values.
}}
\caption{The Three-Task Decoupled Evaluation Framework for Contract Fragility.}
\label{fig:framework}
\end{figure*}

To avoid conflating tool retrieval with parameter extraction and semantic correctness, our protocol isolates model behavior across three orthogonal tasks (Fig.~\ref{fig:framework}):

\subsection{Task 1: Argument Construction}
In Task 1, exactly one correct tool is provided in the prompt, eliminating selection ambiguity. The model is presented with a frozen user query and must construct arguments conforming to the provided schema. Outputs are deterministically validated using JSON Schema Draft-07 validation. Failure modes are categorized into:
\begin{itemize}
    \item \texttt{MISSING\_REQUIRED\_FIELD}: Omission of mandatory contract parameters.
    \item \texttt{TYPE\_MISMATCH}: Parameter generated with invalid type (e.g., string instead of integer).
    \item \texttt{ENUM\_VIOLATION}: Value generated outside allowable enum constants.
    \item \texttt{UNEXPECTED\_FIELD}: Generation of unrequested parameters not defined in schema.
\end{itemize}

\subsection{Task 2: Tool Selection}
In Task 2, the target tool is embedded alongside domain-matched, plausible distractor tools. To prevent positional bias, the presentation order of tools in the prompt menu is randomized with a deterministic seed. We evaluate whether tool-level naming and description ambiguity degrade Top-1 tool selection accuracy.

\subsection{Task 3: Execution Semantics}
Task 3 evaluates outputs that successfully pass syntactic schema validation. A payload may be structurally valid according to JSON Schema but semantically ungrounded. We implement recursive field-by-field evaluation comparing flattened paths, measuring Exact Match (EM), Field Precision, and Field Recall against human-verified ground-truth arguments.

\section{Dataset Specification \& Mutation Taxonomy}

\subsection{Synthetic Specification Corpus}
The dataset comprises 20 synthetic tool specifications modeled after production REST and MCP API conventions across four industry sectors:
\begin{enumerate}
    \item \textbf{Fintech \& Billing:} Stripe refunds, customer invoicing, payment captures.
    \item \textbf{Developer Tools \& Cloud:} GitHub issue tracking, Kubernetes deployment scaling, AWS S3 provisioning, Docker runtime execution.
    \item \textbf{Enterprise CRM \& Communications:} CRM lead status routing, Zendesk ticket triage, Twilio SMS dispatch, Slack alerting.
    \item \textbf{Infrastructure \& Observability:} Datadog monitoring alerts, PagerDuty incidents, Cloudflare CDN cache invalidation, Elasticsearch indexing.
\end{enumerate}

\subsection{Controlled Structural Mutations}
For each base schema, we programmatically construct four controlled variants holding user intent frozen:
\begin{itemize}
    \item \textbf{Canonical (Baseline):} Clean, flat parameter hierarchy with explicit domain nouns and complete docstrings.
    \item \textbf{Nested Hierarchy:} Parameters are encapsulated into a nested sub-object (\texttt{request\_payload}), introducing hierarchical depth.
    \item \textbf{Optionality Bloat:} Six optional enterprise metadata properties (\texttt{tags}, \texttt{correlation\_id}, \texttt{idempotency\_key}, \texttt{priority\_level}, etc.) are appended.
    \item \textbf{Ambiguous Identifiers:} Explicit names are replaced with truncated abbreviations and generic tokens (\texttt{process\_action}, \texttt{target\_id}, \texttt{qty}, \texttt{val}) across both tool-level and parameter-level descriptors.
\end{itemize}

\section{Experimental Protocol and Target Hypotheses}

\subsection{Testable Research Hypotheses}
The benchmark protocol is designed to test three foundational hypotheses:
\begin{itemize}
    \item \textbf{H1 (Nesting Fragility):} Encapsulating flat parameters into nested sub-objects significantly increases schema validation failure rates, primarily driven by parameter flattening at the root level.
    \item \textbf{H2 (Identifier Disambiguation):} Truncating tool names and parameter descriptors causes statistically significant degradation in Top-1 tool selection accuracy in multi-tool contexts.
    \item \textbf{H3 (Optionality Clutter):} Appending high-density optional parameters inflates prompt token overhead without improving task success, inducing hallucination of default arguments.
\end{itemize}

\subsection{Statistical Methodology}
To ensure mathematical rigor, all evaluations enforce:
\begin{itemize}
    \item \textbf{Wilson Score Confidence Intervals:} 95\% confidence intervals computed for all binary proportions.
    \item \textbf{McNemar's Paired Exact Tests:} Evaluated on discordant pairs between baseline and mutated conditions to determine statistical significance ($p < 0.05$).
    \item \textbf{Infrastructure Separation:} HTTP availability failures (e.g., 429 throttling) are strictly isolated from model accuracy scoring.
\end{itemize}

\section{Static Schema Linting (\texttt{SchemaFragilityLinter})}
As an engineering artifact, we release \texttt{SchemaFragilityLinter}, a static analysis utility that audits JSON Schema contracts for known failure patterns prior to deployment:
\begin{itemize}
    \item \texttt{DEEP\_HIERARCHICAL\_NESTING}: Flags nested object hierarchies exceeding 1-level depth.
    \item \texttt{AMBIGUOUS\_IDENTIFIER}: Flags generic or truncated parameter names (\texttt{id}, \texttt{data}, \texttt{val}).
    \item \texttt{EXCESSIVE\_OPTIONALITY\_BLOAT}: Flags schemas where optional properties exceed required properties by more than 2:1.
    \item \texttt{MISSING\_PARAMETER\_DOCSTRING}: Flags parameters lacking semantic documentation.
\end{itemize}

\section{Conclusion and Next Steps}
This paper establishes the formal specification and evaluation protocol for contract fragility in LLM function calling. By decoupling evaluation into argument construction, tool selection, and execution semantics, this framework provides a standardized testbed to assess how schema design choices govern reliability. The full benchmark testbed, dataset, and static linter are open-sourced to facilitate reproducible agent engineering.
